1. What Frydai is

Frydai is an AI e-commerce operator sold as a subscription. A store owner pays once (€149 / 4 weeks, single plan) and gets a private AI agent that lives in their own Telegram bot and runs real work: competitor research, ad creative generation, ad launches, landing pages, Shopify store ops, review responses, abandoned-cart recovery, and more.

The pitch: "not a SaaS dashboard you operate — an operator you delegate to." The customer talks to it in Telegram like a team member ("Frydai, scrape my competitors", "Frydai, run my ads") and it ships the work back.

Two distinctive architecture choices

  1. One container per customer. Every paying customer gets their own isolated Docker container running the Hermes Agent (NousResearch) wired to their own Telegram bot and API keys. No shared multi-tenant agent runtime.
  2. The product is two halves that barely share code. A Next.js marketing site + customer dashboard (app/, lib/) handles signup, billing, the setup wizard, and settings. A per-customer operator image (operator/) is the actual agent. The dashboard provisions and configures operator containers; the operator does the work.
This repo is a port: Frydai was built by porting an older product ("The AI Operator", theaioperator.nl, owned by Leon) onto a new, cleaner stack. The port is essentially complete; current work is hardening, polish, and production cutover.

2. The mental model

Coolify = deploy control plane on Hetzner that runs the containers. GHCR = where the operator Docker image is published by CI.

The single most important sentence: the Next.js app stores the source of truth in Supabase, compiles per-customer config, pushes it to Coolify as container env vars, and Coolify boots/restarts the operator container, whose entrypoint.sh turns those env vars into files on disk that Hermes reads at startup. Almost every feature is a variation on that pipeline.

4. The customer lifecycle

The spine of the product — follow it end to end.

  1. Marketing site (app/page.tsx) → "Deploy Frydai" → Whop checkout (external, single plan).
  2. Whop billing. On purchase:
    • Webhook → /api/webhooks/whop → verify signature → upsert customers in Supabase (active/trialing).
    • Whop OAuth (/api/auth/whop/start → callback) → mint Frydai session JWT (HS256) in httpOnly frydai_session cookie.
  3. Setup wizard (app/setup/page.tsx). Customer enters:
    • Required: Telegram bot token + OpenAI API key.
    • Optional: Shopify, Meta, Airtable, Apify, Gemini, HiggsField, Email, WhatsApp.
    • Business profile → becomes SOUL.md / AGENTS.md.
  4. Provisioning — wizard POSTs to /api/activate:
    1. Re-check session + live membership (fails closed).
    2. Validate bot token via Telegram getMe.
    3. Create/reuse Coolify application from operator image.
    4. Set per-customer env vars (incl. base64 SOUL_MD_CONTENT / AGENTS_MD_CONTENT).
    5. Start container.
    6. Write coolify_app_uuid, bot_username, status=active to Supabase.
  5. Container boots — entrypoint.sh: validate env, write config files, restructure skills, exec hermes gateway run.
  6. Live. Customer DMs their Telegram bot. Hermes has full business context from SOUL.md/AGENTS.md.

After setup, dashboard settings (app/dashboard/settings/) use /api/dashboard/update-keys and /api/dashboard/update-profile — recompile context, push env to Coolify, restart container (5–15s blip).

6. The operator container

The heart of the product. Source: operator/.

Build (Dockerfile)

Clones hermes-agent, installs Python 3.13 + uv + Node 20, copies skills/tools/mcp/entrypoint. CI builds and pushes to GHCR on every operator/ change to main.

Boot (entrypoint.sh)

  1. Fail-fast — exit 1 without TELEGRAM_BOT_TOKEN or OPENAI_API_KEY.
  2. Install skills — flat skills/*.md → $HERMES_HOME/skills/<stem>/SKILL.md. Slash command == filename stem == name: frontmatter.
  3. Write config.yaml — model + OpenAI provider. Meta Ads MCP block only if Meta creds present.
  4. Write .env — all platform credentials (keep in sync with registry.ts; check-entrypoint-sync.mjs enforces).
  5. Write context files — base64-decode SOUL → /opt/data/SOUL.md, AGENTS → /opt/hermes/AGENTS.md.
  6. exec hermes gateway run

Why base64?

Coolify serializes env to a .env file without quoting. Docker's parser breaks on newlines; compiled Markdown is always multi-line. Base64 makes each value single-line.

Why restart on profile change?

Hermes reads SOUL.md/AGENTS.md once at session init — no hot reload. Deliberate design choice, not a bug.

9. The skills system

Skills are Markdown instruction files in operator/skills/ — prose procedures the LLM follows. 40+ files in repo; 21 hardened customer-facing skills.

How a skill becomes a command

skills/<name>.md → Dockerfile → entrypoint restructures → $HERMES_HOME/skills/<name>/SKILL.md → Hermes registers /<name>.

21 core skills by family

  • A. Ad pipeline — scrape-ads, competitor-research, script-ads, image-prompt-architect, generate-ad-statics, static-to-video, ad-order, launch-ads, orchestrated by ad-machine
  • B. Shopify ops — store-health-monitor, abandoned-cart-rescuer, listing-optimizer, review-responder, order-status-updater
  • C. Setup/config — onboard, my-business
  • D. Standalone — build-page, video-analyzer, summarize
  • E. Meta-skills — skill-builder, skill-creator

Bulletproof Skill Standard (12 criteria)

  • Credential preflight — check env vars before work; friendly "not connected" messages via preflight.sh
  • Tool contract — external work via tools/*.sh, one machine-readable line (OK/FALLBACK/SKIP/ERROR). Never inline multi-line curl/jq in skill body.
  • Confirm-gating — spending money or publishing externally requires customer confirmation
  • Graceful degradation — optional integrations degrade cleanly; partial success continues the batch

Gold-standard references: generate-ad-statics.md and store-health-monitor.md.

Dual-vendor creative path

HiggsField connected → HiggsField REST (Soul 2.0 / FLUX) + DoP video. Otherwise → confirm-gated fallback to OpenAI gpt-image-1 + ffmpeg Ken Burns. HiggsField auth is static REST key+secret — no OAuth/MCP (headless containers can't do browser redirect).

16. Your first week

  1. Read (in order): this doc → operator/README.md → docs/hermes-context-lifecycle.md → SKILL_STANDARD.md → SKILL_PLATFORM_MATRIX.md
  2. Trace one request: app/setup/page.tsx → app/api/activate/route.ts → operator/entrypoint.sh
  3. Run locally: npm install && npm run dev, set FRYDAI_DEV_MOCK=1, click through wizard with dev mock. Build operator image in WSL.
  4. Read one gold-standard skill: generate-ad-statics.md + tools/generate_static.sh
  5. Make a tiny safe change: add a field to registry.ts, run npm run lint — watch entrypoint-sync catch missing env var.
  6. Before any backend change, run npm test and npm run validate:skills.

Welcome aboard. When in doubt, the source of truth is the code and reference docs in docs/ + operator/ — this cookbook is the map, not the territory.
